# 開発プロセス

タスク管理とメモを統合した CLI アプリを、Claude Code と協働して開発するためのプロセス。

## 前提

| 項目 | 決定事項 |
| --- | --- |
| 目的 | 自分で日常的に使うツール（実用性を最優先） |
| 進め方 | テスト駆動開発（TDD）中心 |
| 言語 | Go |
| バージョン管理 | GitHub で PR 運用 |
| タスク管理 | GitHub Issues |
| CI | GitHub Actions |
| 記述言語 | すべて日本語（Conventional Commits の type プレフィックスのみ英語） |

## 全体の流れ

1 機能 = 1 Issue = 1 ブランチ = 1 PR で進める。

```
Issue作成 → 仕様メモ → [承認] → ブランチ作成
  → Red → [承認] → commit
  → Green → [承認] → commit
  → Refactor → [承認] → commit
  → (必要に応じて Red から繰り返す)
  → PR作成 → Claudeセルフレビュー → 修正 → CIグリーン → 人間がマージ
  → PRの気づきを記録
  → (5PRごとに) 振り返り → プロセス改善PR
```

`[承認]` は人間（開発者）の確認ポイント。Claude は承認を得るまで次のステップに進まない。

## 各フェーズの詳細

### 1. Issue 作成

- 機能・改善・バグごとに GitHub Issue を作成する。
- Issue には目的（なぜ必要か）と完了条件を簡潔に書く。

### 2. 仕様メモ

- `docs/specs/<番号>-<機能名>.md` に機能ごとの軽量な仕様を書く（例: `docs/specs/001-add-task.md`）。
- 含める内容:
  - 概要（1〜3 行）
  - コマンド例と期待される出力
  - 正常系・異常系の振る舞い
  - スコープ外とすること
- **承認ポイント**: 開発者が仕様メモを承認してから実装に着手する。

### 3. ブランチ作成

- `main` から機能ブランチを切る。
- 命名: `<type>/<issue番号>-<短い説明>`（例: `feat/12-add-task`, `fix/15-date-parse`）

### 4. TDD サイクル

各ステップの完了時に Claude は作業を止め、開発者の承認を得てからコミットする。

| ステップ | Claude の作業 | 承認時に確認すること | コミット |
| --- | --- | --- | --- |
| Red | 仕様メモに基づき失敗するテストを書き、失敗することを確認する | テストが仕様を正しく表しているか | `test: ...` |
| Green | テストを通す最小限の実装を書く | テストが通ったか、実装が過剰でないか | `feat: ...` / `fix: ...` |
| Refactor | テストを通したまま設計・可読性を改善する（不要ならスキップを提案） | 振る舞いを変えていないか | `refactor: ...` |

- 1 サイクルは小さく保つ。1 つの仕様項目（コマンド例 1 つ程度）を 1 サイクルの目安とする。

### 5. PR 作成とレビュー

- 機能が完成したら PR を作成し、本文に `Closes #<issue番号>` を記載する。
- PR 本文には変更概要・仕様メモへのリンク・動作確認方法を書く。
- Claude が `/code-review` でセルフレビューし、指摘があれば修正する。
- CI がグリーンであることを確認する。
- **マージは開発者が行う。** Claude はマージしない。

### 6. PR ごとの気づきの記録

- PR のマージ後、Claude が `docs/retrospectives/notes.md` にその PR での気づきを 1〜3 行で追記する。
- 対象はプロダクトではなく**プロセス**についての気づき（例: 承認待ちが多すぎた、仕様メモの粒度が粗かった、テストが書きにくかった）。
- Claude が案を出し、開発者が追記・修正して確定する。
- `notes.md` は `.gitignore` 対象のローカルファイルで、**コミットしない**。内容は振り返り時に振り返りファイルへ転記され、プロセス改善 PR でコミットされる。

## プロセス改善

このプロセス自体を継続的に改善する。

**機能開発の PR とプロセス改善の PR は必ず分ける。** 機能ブランチにはプロセス関連のファイル（`docs/development-process.md`、`CLAUDE.md` のプロセス記述、`docs/retrospectives/`）の変更を含めない。

### 振り返り（5 PR ごと）

- 前回の振り返り以降にマージされた PR が 5 件に達したら、Claude が振り返りの実施を提案する。件数は `notes.md` の未振り返りの記録数で判断する。
- 開発者は 5 件未満でも任意のタイミングで振り返りを依頼できる。
- 形式は **KPT**。`notes.md` の記録と、その間の PR・コミット履歴をもとに Claude が下書きし、開発者と対話して確定する。
  - **Keep**: うまくいっていて続けること
  - **Problem**: 問題・やりにくかったこと
  - **Try**: 次に試すこと（プロセスへの具体的な変更案）
- 結果は `docs/retrospectives/<YYYY-MM-DD>-retro-<連番>.md` に保存する（テンプレート: `docs/retrospectives/template.md`）。
- 振り返りに使った `notes.md` の記録は振り返りファイルの「PR ごとの気づき」に転記し、`notes.md` からは削除する。

### 改善の反映

- 振り返りごとに専用のブランチ（`process/retro-<連番>`）を切り、プロセス改善 PR を作成する。
- この PR には振り返りファイルと、採用した Try による `docs/development-process.md`・`CLAUDE.md` の更新を含める（`docs:` プレフィックス）。
- 開発者が承認・マージする。
- PR 本文には元になった振り返りファイルへのリンクを書く。
- プロセスの変更はこの PR を通してのみ行い、変更履歴は Git で追えるようにする。

## テスト方針

- **ユニットテスト**: ドメインロジックを Go 標準の `testing` パッケージでテストする。テーブル駆動テストを基本とする。
- **CLI E2E テスト**: ビルドしたバイナリを実行し、コマンドの入出力を検証する（`testscript` などを利用）。
- **カバレッジ**: `go test -cover` で確認するが、閾値は設けない（目安として参照するのみ）。
- テストはファイルシステム等の副作用を一時ディレクトリに閉じ込め、実環境のデータに触れない。

## 静的解析・フォーマット

- `gofmt` と `go vet` のみを使用する。
- CI で以下をチェックし、失敗したらマージしない。
  - `gofmt -l .` の出力が空であること
  - `go vet ./...` が成功すること
  - `go test ./...` が成功すること

## コミット規約

[Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/) に従う。type は英語、本文は日本語。

| type | 用途 |
| --- | --- |
| `test` | テストの追加・修正（Red） |
| `feat` | 新機能の実装（Green） |
| `fix` | バグ修正 |
| `refactor` | 振る舞いを変えないコード改善 |
| `docs` | ドキュメントのみの変更 |
| `chore` | ビルド・CI・依存関係など |

例: `test: タスク追加コマンドのテストを追加`
